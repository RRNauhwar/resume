Data model

Each record gets a UUID and createdAt. Writes are serialised through a promise queue. Cases themselves are generated on-demand by the LLM (and seeded offline on Android via Room). API flow — one courtroom turn (be able to narrate this)

  1. User types an argument in the Courtroom page; client POSTs to /api/ai/judge-respond (or /lawyer-respond, /witness-answer, /objection) with the recent history + Supabase JWT.
  2. Request passes the middleware chain (headers → rate-limit → JSON validation → CSRF → auth → audit).
  3. Route validates input (assertText, safeArray, safeEnum), then calls the matching service function.
  4. ask(system,user) picks the first configured provider and calls it; last 4 turns of history are included for context.
  5. Response text is returned (or safeJSON-parsed for structured endpoints), wrapped as { success:true, ... }; errors are normalised so 5xx never leaks internals.

Authentication & authorization

Supabase issues JWTs on the client. The backend's requireAuth extracts the Bearer token and verifies it against Supabase /auth/v1/user; verified users get {userId, role, collegeId}. Without a valid token the request is demoted to a guest student (it cannot self-assign a privileged role in production). requireRole([...]) enforces per-endpoint authorization. Six roles exist: student, lawyer, judge, admin, college, recruiter.

  • Provider abstraction: one ask() → OpenAI → Gemini → Anthropic fallback by available key.
  • Functions: generateCase, judgeRespond, aiLawyerRespond, handleObjection (returns sustained/overruled), witnessAnswer (stays in character), analyzePerformance (scored JSON rubric), getLegalSuggestions, evaluateDraft, deliverJudgment, getPrecedents, askBeaksTutor (+ SSE streaming).
